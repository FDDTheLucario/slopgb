# The speed-switch HDMA abort is SOLVED (see `Ppu::hdma_block_m_cycle`): a STOP
# whose pause begins inside the M-cycle that services the line's HBlank block —
# the mode-0 flip plus 5 dots, one M-cycle wide — catches the transfer with the
# core clock already gated, so it aborts with the count latched and FF55 gains
# bit 7. Landing before that M-cycle leaves the transfer running; landing after
# it means the block already went and the transfer completes. Recovered the five
# `hdma_transition_speedchange_hdmalen*` rows plus
# `hdma_late_m3speedchange_hdma5_scx{1,2}_2`. Scoped to a STOP that ENTERS double

# The speedchange TIMA family is SOLVED (`Timer::stop_div_presample`). The STOP
# DIV reset was sampling the divider one M-cycle behind where hardware has it:
# gambatte timestamps the FF04 write at the skipped-byte slot's START, so by the
# time the reset commits the divider has run through that slot. Feeding the timer
# those four T-cycles before the reset lets it see the pre-STOP divider hardware
# sees, and with a fast TAC tap whether the selected bit is still set decides one
# TIMA edge — which was the whole off-by-one. Recovered 14 gambatte rows plus
# age-test-roms/speed-switch/spsw-tima-cgbBC.
# The correction is bracketed to 4..7 T (1..3 are byte-identical, 8 overshoots),
# and 4 is the M-cycle. Two cheaper shapes are refuted: evaluating the reset's
# edge against the later divider without clocking the intermediate T, and
# repositioning the divider without clocking, each cost 6 rows.
# TAC 00 is excluded and that part is measured, not explained — see the comment
# on `stop_div_presample`.
# What is LEFT in speedchange after that fix is 20 rows, and 15 of them are APU:
# nine `ch1_duty0_pos6_to_pos7_timing` variants and six `ch2_nr52`. The nr52 rows
# want F2 and read F0 — channel 2 switched off, so its length counter clocked one
# step too many, the mirror of the timer's missing edge. The timer's remedy does
# NOT transfer: giving the APU the same +4 T divider view before its own
# `div_write` costs a row (20 -> 21). The rest are two `ly44_m3_stat` and one
# `nop_m2int_m3stat_scx1`.
# Three APU shapes refuted, plus a trace that narrows it: evaluating the STOP
# div_write edge with the NEW speed's bit costs a row (20 -> 21), suppressing the
# entering-side div_event the way the leaving side does costs a row, and giving
# the APU the timer's +4 T divider view costs a row. The ch2_nr52 siblings run
# the SAME number of frame-sequencer events (649 each), so the divergence is not
# the event count — it is where the ROM's NR24 length-enable write falls relative
# to a length step. That is the extra-length-clock quirk meeting the switch, not
# the divider pacing.
# A fourth is out too: suppressing the length clock on the write-induced
# div_event costs a row (20 -> 21). Note the phase term these rows turn on is
# `Apu::next_step_clocks_length`, plain divider parity — and the switch's
# `div_write` both advances that divider and clocks lengths, so it moves the
# parity a later NRx4 write is judged against. That coupling is where to look.
# Traced, and it moves the target again: the ch2_nr52 NRx4 writes land BEFORE the
# switch (div_divider 0, next_step_clocks_length true, prev_div 0x0FFC so bit 12
# is clear and the switch raises no div_event at all). Both siblings are
# byte-identical in slopgb at that point, so the phase at the write is NOT what
# separates them — hardware's frame-sequencer step boundary must fall between the
# two writes, four T apart, where slopgb puts both in one step. Shifting the APU's
# divider view does not express that: +4/+8 costs eight rows, -1/-2/-4 costs five.
# So the boundary is inside the FS step placement, not a constant offset applied
# to the divider it reads.
# Stepping the frame sequencer at T-cycle granularity — splitting the DIV-APU
# edge out of `Apu::tick` and running it four times per machine cycle while the
# channels still advance once — is NEUTRAL (20 either way). That rules the
# granularity out: under tick-then-access the NRx4 write already observes the APU
# stepped through the whole preceding machine cycle, which is as fine as the
# contract allows. Seven shapes eliminated on this family now; the next attempt
# should question the CONTRACT (when the write samples the APU) rather than the
# APU's own resolution.
# Traced to the exact instant. For ch2_nr52 the NR52 READ lands at FS divider 3,
# in the same machine cycle as the length clock that disables channel 2 — and
# under tick-then-access the read always sees the post-clock state, so slopgb
# returns F0 for BOTH siblings. Hardware separates them there: the `1a` read
# falls before that length clock (F2), the `1b` read after it (F0). So the whole
# family is one ordering question — the CPU read versus the length clock inside
# one machine cycle — not divider pacing, not FS resolution.
# Two more shapes eliminated: shifting which step the NRx4 write samples
# (both directions cost eight rows, and they are blargg-pinned), and deferring
# the length clock by one machine cycle (20 -> 22). Eight eliminations total.
# The tick order is REFUTED too, and cheaply: deferring the whole APU step by one
# machine cycle — so an access sees the APU as of the cycle's start — costs nine
# rows (20 -> 29). That was the hypothesis worth fearing, and it is now measured
# instead. Nine eliminations on this family.
# That shape is tried and eliminated too: snapshotting the pre-clock channel bits
# and returning them from FF26 whenever the length clock landed in the same
# machine cycle costs two rows (20 -> 22). It has to — `1b` wants the POST-clock
# value from the same machine cycle `1a` wants the PRE-clock one.
# So the requirement is now exact, and it is the last shape standing: the FF26
# read needs a sub-M-cycle POSITION compared against the length clock's own
# position, the way `Ppu::read_pos_hd` is compared against the render's flip.
# slopgb's APU has no such read position — that is the piece to build.
# The boundary is now measured to the cycle. On speedchange_ch2_nr52, the length
# clock that disables channel 2 runs at interconnect cycle 94238; `1a` reads at
# 94238 (SAME machine cycle, wants the PRE-clock F2) and `1b` at 94240 (the next
# one, wants POST-clock F0). So the law is simply: a read in the length clock's
# own machine cycle sees the pre-clock value.
# Implementing that as a snapshot latched in `clock_lengths` and cleared at the
# top of `Apu::tick` does NOT reproduce it — the `_1b`/`_2b` rows break and the
# `_1a`/`_2a` rows stay broken, so the snapshot's lifetime is not the machine
# cycle those reads straddle. Getting that lifetime right — probably by keying the
# snapshot to the interconnect's cycle counter rather than to the APU tick.
# BUILT and measured: keying it to the interconnect cycle works exactly as traced
# — `_1a` matches the clock's cycle and gets the pre-clock bits, `_1b` does not
# and gets the live ones — and it FIXES all six `_a` rows. But it breaks eight
# `_b` rows (speedchange2/3/4 `_1b`/`_2b`, speedchange `_ds_1b`/`_2b`), which read
# in a disabling clock's own cycle and still want the POST-clock value. So cycle
# equality is not the whole discriminator: something separates an `_a` read from a
# `_b` read at the same offset. That is the last unknown — everything else about
# this family is now measured. Twelve shapes eliminated.
# Speed is NOT that discriminator: scoping the rule to single speed costs six
# more rows (20 -> 26) — but scoping it to DOUBLE speed is nearly right, and the
# measurement behind that is the useful part. Clock cycle against read cycle:
#   speedchange  _1a  read 94238, clock 94238 (same), DS, wants PRE
#   speedchange  _1b  read 94240, clock 94238,        DS, wants POST
#   speedchange2 _1a  read 225507, clock 209127,      SS, wants PRE
#   speedchange2 _1b  read 225511, clock 225511 (same), SS, wants POST
# So a same-cycle read wants PRE in double speed and POST in single — the machine
# cycle is two dots against four, so the read sits ahead of the clock only in DS.
# The DS-scoped rule recovers four speedchange rows (20 -> 16) but breaks four
# gambatte/sound DS rows (ch2_late_div_write_nr52_ds_1b/2b, ch2_late_reset_nr52
# _ds_1b, ch2_reset_length_counter_timing_nr52_ds_2) which are ALSO same-cycle DS
# reads and want POST. The one thing separating those from the speedchange ones is
# that the speedchange reads follow a speed SWITCH.
# And the sub-cycle offset does NOT separate them either — measured: the two
# cases are identical in every quantity the model holds.
#   speedchange _1a   clk cyc 94238, div C000, div&3 = 0, DS, read 94238, wants PRE
#   sound ch2_late_div_write_nr52_ds_1b
#                     clk cyc 94284, div C000, div&3 = 0, DS, read 94284, wants POST
# Same cycle, same divider phase, same speed, opposite answers. So the
# discriminator is not present in the model at all, which is why fifteen shapes
# have now failed on it. The one modelled quantity that differs between the two
# situations is `Apu::set_double_speed_lag`, the one-machine-cycle APU re-pace a
# switching STOP installs — but gating the rule on a post-switch alignment flag
# changes NOTHING (still 16 speedchange + 4 sound), because the `sound _ds_` ROMs
# reach double speed through a switching STOP as well, so the flag is set for both
# sides. Even "did a switch happen" does not separate them.
# Sixteen shapes eliminated. The state of knowledge: the pre/post law is exact and
# measured, the DS-scoped form recovers four rows, and the last discriminator is
# absent from the model AND from every proxy tried for it. Resolving it needs the
# frame sequencer's step to carry a real T-position within the machine cycle.
# FOUND, in SameBoy 1.0.2 `Core/timing.c` (the divider coroutine, ~line 275):
#     GB_SLEEP(gb, div, 1, 3);
#     while (true) {
#         advance_tima_state_machine(gb);
#         GB_set_internal_div_counter(gb, gb->div_counter + 4);
#         ...
#         GB_SLEEP(gb, div, 2, 4);
#     }
# The divider advances in 4-cycle steps, but the loop opens with a THREE-cycle
# sleep — so every div update, and with it the APU div event and the length
# clock, sits at T-offset 3 of the machine cycle rather than on its boundary.
# slopgb has no such offset: `Apu::tick` runs the whole step at the cycle's end.
# That offset is the missing quantity. Applying it means giving the length clock
# a position of 3 within the machine cycle and comparing the FF26 read's own
# position against it, which also needs the read to carry a position — the same
# `read_pos_hd` shape the PPU already has.
# CORRECTION, measured with a SameBoy 1.0.2 tester patched to trace the length
# clock and the NR52 read: SameBoy READS NR52 ONCE in each of these ROMs and
# reports channel 2 INACTIVE for `_1a` as well as `_1b` — that is, SameBoy gets
# the same answer slopgb does and FAILS the `_1a` expectation. So SameBoy cannot
# supply the missing T-offset for this family; it does not reproduce the
# behaviour. gambatte does (these `_outN` values are its suite, hardware-checked),
# so gambatte's APU length/frame-sequencer model is the reference to read here,
# not SameBoy's. The T-offset 3 noted above is SameBoy's divider placement and
# may simply be the wrong model for this corner.
# NOT by re-seeding the divider: SameBoy starts it at 8 (`gb.c`
# GB_set_internal_div_counter(gb, 8)) but slopgb's boot DIV is installed directly
# and pinned by mooneye boot_div-cgbABCDE / -A and the gambatte div/start_inc
# rows, so that phase is already oracle-fixed. The offset belongs to the APU's
# step position inside the machine cycle, not to the divider's seed.
